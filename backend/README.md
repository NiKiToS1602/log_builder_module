# Бэкенд конструктора журналов

Стартовое приложение Spring Boot 4.1.2 с Spring MVC и Actuator. Для локального запуска установите JDK 21 и укажите его в `JAVA_HOME`. Для первой сборки нужен доступ к Maven Central. Maven Wrapper входит в проект.

В IntelliJ IDEA откройте `backend/pom.xml` как Maven-проект или подключите этот файл в окне Maven уже открытого репозитория. Выберите JDK 21 как Project SDK и Maven Wrapper как версию Maven. После синхронизации запустите класс `LogBuilderApplication`.

Для запуска приложения подготовьте базу PostgreSQL и пользователя с правом создавать объекты в её схеме. По умолчанию приложение подключается к базе `log_builder` на localhost:5432 под пользователем `log_builder`. Параметры подключения задаются через `DB_URL`, `DB_USER` и `DB_PASSWORD`; в IntelliJ IDEA их можно задать в конфигурации запуска. При старте Flyway применяет миграции V1–V8, затем Hibernate проверяет соответствие моделей схеме.

Для локальных параметров также поддерживается файл `backend/.env` с ключами `DB_URL`, `DB_USER` и `DB_PASSWORD`. Он загружается при запуске из корня репозитория или каталога `backend` и исключён из Git. Переменные окружения имеют приоритет над значениями файла.

Для сборки и запуска из корня репозитория выполните в PowerShell:

```powershell
cd backend
.\mvnw.cmd clean verify
.\mvnw.cmd spring-boot:run
```

В другом окне выполните `Invoke-RestMethod http://localhost:8080/actuator/health`. У запущенного приложения поле `status` равно `UP`. Чтобы остановить сервер, нажмите Ctrl+C.

Swagger UI доступен по адресу http://localhost:8080/swagger-ui/index.html, спецификация OpenAPI — http://localhost:8080/v3/api-docs. Документация формируется автоматически по REST-контроллерам. По мере реализации API его операции будут появляться в Swagger UI.

## API журналов (задачи № 25, № 31 и № 39)

Базовый путь — `/api/v1/journals`. Идентификаторы шаблонов и журналов передаются как UUID, идентификаторы филиалов — как целые числа.

| Запрос | Результат |
| --- | --- |
| `POST /` | Принимает `{name, templateId, templateVersion, locationId, responsibleUid?, startDate?, schedule?}`. Создаёт активный журнал по существующему активному шаблону, возвращает `201`, заголовок `Location` и карточку. |
| `GET /` | Возвращает `{items, page, size, hasNext}`. `page` начинается с 0, `size` по умолчанию 50 и принимает значения от 1 до 100. Порядок — по убыванию времени создания и UUID. `includeArchived=true` включает архивные журналы. |
| `GET /{id}` | Возвращает карточку `{journal, columns, startDate, schedule}` с метаданными и неизменяемым снимком полей, в том числе для архивного журнала. |
| `PUT /{id}` | Принимает `{name, responsibleUid, version, startDate?, schedule?}` и возвращает обновлённую карточку активного журнала. `null` или отсутствие `responsibleUid` снимает назначение. |
| `DELETE /{id}?version=0` | Архивирует журнал и возвращает `204`. Передайте текущую версию из карточки. Повторная архивация возвращает `204` без повторной записи аудита. Записи, поля и расписание сохраняются. |

При архивации активного журнала сервер проверяет ячейки подтверждения. Подтверждённые ячейки и прочерки допускаются. Если остались неподтверждённые ячейки, сервер возвращает `409` с пояснением в `detail`. Статус, версия и аудит в этом случае сохраняют прежние значения. Проверка и смена статуса выполняются под блокировкой журнала, которую также берут операции записи и подтверждения.

`startDate` и даты внутри расписания передаются в формате `YYYY-MM-DD`. При создании с датой начала расписание по умолчанию имеет `frequency: "none"`. Если старый запрос на создание не передал дату и расписание, оба значения в карточке будут `null`. При редактировании отсутствие или `null` сохраняет текущее значение даты и расписания. Передайте `{"frequency":"none"}`, чтобы отключить расписание и сохранить дату начала. Изменение только даты или расписания тоже увеличивает версию журнала и записывается в аудит.

| `schedule.frequency` | Параметры |
| --- | --- |
| `none` | Заполнение по необходимости. |
| `once` | Заполнение в дату начала. |
| `daily` | `interval` в днях, необязательный `endDate` включительно. |
| `weekly` | `interval` в неделях, `weekdays` от 1 (понедельник) до 7, необязательный `endDate`. |
| `monthly` | `interval` в месяцах, `monthDays` от 1 до 31 и/или `lastDay: true`, необязательный `endDate`. |
| `yearly` | `interval` в годах, одно число в `monthDays`, месяц из `startDate`, необязательный `endDate`. Поддерживает ранее записанные годовые расписания. |
| `custom` | Непустой список `dates` начиная с даты начала журнала. |

Для вариантов кроме `none` можно передать `times` со значениями в формате `HH:mm`. Они хранятся как местное время без смещения. Ограничения расписания проверяются до записи в PostgreSQL.

Чтение доступно ролям `owner`, `manager` и `employee`, изменение — `owner` и `manager`. Каждая операция ограничена организацией и действующим списком разрешённых филиалов из проверенного контекста. Недоступный журнал по прямому ID возвращает `404`. Устаревшая версия возвращает `409`, ошибки значений — `422`. Изменения журнала и аудит фиксируются в одной транзакции. Для аудита профиль пользователя должен присутствовать в локальном каталоге с заполненным именем.

Точка подключения аутентификации — атрибут текущего запроса `JournalAccess.REQUEST_ATTRIBUTE` типа `JournalAccess`. Его устанавливает серверный фильтр после проверки сессии и интроспекции по [спецификации ClearBarn](../docs/39_CLEARBARN_SIGN_IN_SERVICE_SPEC.md). При подключении cookie-сессии фильтр также должен проверять CSRF для изменяющих запросов. Фильтр ClearBarn в этом этапе отсутствует. Без подтверждённого контекста API возвращает `401`. Контрактные тесты устанавливают атрибут на серверной стороне MockMvc и используют временную PostgreSQL.

## Интеграционные проверки (задача № 43)

`mvnw.cmd clean verify` запускает проверки REST-контракта на отдельном временном экземпляре PostgreSQL. Тесты покрывают создание и редактирование журнала, область доступа, версии, аудит, миграции и конфликт архивации с параллельной записью. Карточка журнала без выбора конкретных подписантов читается за три SQL-запроса. Для проверки перед архивацией добавлен частичный индекс неподтверждённых ячеек.

После сборки приложение можно запустить из каталога `backend` командой PowerShell `& "$env:JAVA_HOME/bin/java.exe" -jar target/log-builder-0.0.1-SNAPSHOT.jar`.
