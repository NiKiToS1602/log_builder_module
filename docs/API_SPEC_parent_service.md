# API для внешних модулей: сотрудники и филиалы

Версия документа: 2026-10-27. Контракт соответствует текущему коду post-MVP
контура. Наличие реализации в репозитории **не подтверждает её публикацию** на
рабочем сервере: адрес API и доступность режима должен сообщить оператор.

Документ предназначен разработчику внешнего сервиса. Внутренний контракт
владельцев и интеграций описан в
[32_EXTERNAL_DIRECTORY_AND_OWNER_MANAGEMENT.md](32_EXTERNAL_DIRECTORY_AND_OWNER_MANAGEMENT.md),
рекомендации по запуску синхронизации — в
[33_EXTERNAL_DIRECTORY_CONSUMER_GUIDE.md](33_EXTERNAL_DIRECTORY_CONSUMER_GUIDE.md).

## 1. Назначение и общие правила

Внешний модуль может автоматически читать каталог владельцев (`owner`),
менеджеров (`manager`), сотрудников (`employee`) и филиалов одной организации.
Изменять эти записи через данный API нельзя. Все маршруты имеют префикс
`/api/v1`, используют JSON и доступны только в post-MVP режиме
(`MVP_SCOPE_ENABLED=false`). Base URL далее обозначен как
`https://directory.example.test`; это вымышленный адрес.

Организация определяется **только** по проверенному токену интеграции.
Параметра `organization_id` в запросах каталога нет; данные другой
организации не раскрываются. Токены пользователей и терминалов не дают
доступ к каталогу. Успешные ответы и ошибки каталога отправляются с
`Cache-Control: no-store` и `Pragma: no-cache`.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/external/auth/token` | Обменять `client_id` и `client_secret` на токен интеграции |
| `GET` | `/api/v1/external/directory/members` | Снимок участников с пагинацией |
| `GET` | `/api/v1/external/directory/members/{member_uid}` | Карточка участника |
| `GET` | `/api/v1/external/directory/locations` | Снимок филиалов с пагинацией |
| `GET` | `/api/v1/external/directory/locations/{location_id}` | Карточка филиала |
| `GET` | `/api/v1/external/directory/changes` | Изменения после снимка |

## 2. Авторизация внешнего модуля

Владелец организации выпускает один `client_id` (UUID) и секрет интеграции
через административный интерфейс. Секрет показывается только при выпуске или
ротации. Для одной организации предусмотрен один integration client;
несколько внешних модулей, использующих его, разделяют лимит и аудит.
Выдача и отзыв секретов выполняются владельцем, а не внешним модулем.

### Получение токена

```http
POST /api/v1/external/auth/token HTTP/1.1
Host: directory.example.test
Content-Type: application/json

{
  "client_id": "00000000-0000-4000-8000-000000000007",
  "client_secret": "FAKE-EXAMPLE-SECRET"
}
```

Успешный ответ `200 OK`:

```json
{
  "data": {
    "access_token": "<opaque-bearer-token>",
    "token_type": "bearer",
    "expires_in": 1800,
    "scope": "directory:read"
  }
}
```

Обмен допускает только HTTPS, `Content-Type: application/json` и JSON-объект
ровно с полями `client_id` (непустая строка, до 128 символов) и
`client_secret` (непустая строка, до 512 символов). Параметры query не принимаются;
максимальный размер тела — 4096 байт. Токен действует 30 минут, refresh token
не выдаётся. Для всех GET передавайте:

```http
Authorization: Bearer <access_token>
```

Переиспользуйте токен до истечения срока. Лимит обмена — 5 запросов в минуту
на `client_id` и 20 в минуту на IP, включая неудачные попытки. При `429`
соблюдайте `Retry-After`. Отзыв секрета запрещает новые обмены, но уже
выданный access token действует до `exp`, пока client и организация активны.
Храните секрет и токен только на сервере, не передавайте их в URL или логи.

### Два режима каталога

| `include_inactive` | Состав | Изменение статуса в `/changes` |
|---|---|---|
| отсутствует или `false` | Действующие записи | `remove`, когда запись выходит из действующего состава |
| `true` | Все **сохранённые** записи, включая неактивные, уволенные и архивные | `upsert` с полной карточкой нового статуса |

Для полного справочника запрашивайте **оба** снимка с
`include_inactive=true`. Выбранный режим закреплён в курсорах. При смене режима
сделайте новый снимок участников и новый снимок филиалов. Физически удалённые
записи API не восстанавливает.

## 3. Объекты ответа

### Участник (`Member`)

| Поле | Тип | Значение |
|---|---|---|
| `member_uid` | UUID string | Постоянный глобально уникальный идентификатор записи участника; используйте как ключ синхронизации |
| `full_name` | string | ФИО |
| `role` | `owner \| manager \| employee` | Роль участника; не список детальных разрешений |
| `status` | enum | Статус членства, см. ниже |
| `updated_at` | ISO 8601 datetime | Последнее изменение учтённых записей участника, назначений или связанных сущностей; может измениться без смены остальных полей DTO |
| `primary_location` | `Reference \| null` | Основной филиал |
| `locations` | `Reference[]` | Филиалы участника в выбранном режиме |
| `primary_position` | `Reference \| null` | Основная должность |
| `positions` | `Reference[]` | Должности участника в выбранном режиме |
| `location_scope` | `organization \| assigned_locations` | Область филиалов: вся организация у owner, назначения у остальных |

`Reference` имеет ровно `id` (положительное целое) и `name` (строка).
У owner `primary_location=null`, `primary_position=null`, `positions=[]`;
`locations` содержит действующие филиалы в обычном режиме и все сохранённые
филиалы организации в полном. В полном режиме назначения сотрудника включают
также сохранённые неактивные связи и архивные цели. Поэтому `locations` и
`positions` полного режима **не подтверждают текущий доступ** к ним.
Если в сохранённых исторических связях несколько признаков `is_primary`,
проекция выбирает последнюю связь по ID цели.

Статусы участника: `active`, `inactive`, `suspended`, `terminated`, `archived`.
`archived` имеет приоритет, если архивирована учётная/кадровая запись.
Отменённое приглашение owner отображается как `inactive`, если он не архивен.
Неактивированная учётная запись может иметь статус членства `active`:
`status` не означает возможность входа. Отдельного `access_status` нет.

Пример полной карточки уволенного сотрудника:

```json
{
  "member_uid": "00000000-0000-4000-8000-000000000008",
  "full_name": "Иванов Иван Иванович",
  "role": "employee",
  "status": "terminated",
  "updated_at": "2026-10-27T10:00:00Z",
  "primary_location": {"id": 7, "name": "Центр"},
  "locations": [{"id": 7, "name": "Центр"}],
  "primary_position": {"id": 3, "name": "Бариста"},
  "positions": [{"id": 3, "name": "Бариста"}],
  "location_scope": "assigned_locations"
}
```

`member_uid` не является электронной подписью, цифровым доказательством
действия сотрудника или способом его аутентификации. Логин, телефон, пароли,
коды активации и учётные метаданные в этом DTO не передаются.

### Филиал (`Location`)

| Поле | Тип | Значение |
|---|---|---|
| `id` | integer | ID филиала, ключ синхронизации внутри организации |
| `name` | string | Название |
| `address` | `string \| null` | Адрес |
| `status` | `active \| inactive \| archived` | Статус; `archived` имеет приоритет над обычным статусом |
| `updated_at` | ISO 8601 datetime | Время последнего изменения |
| `legal_entity` | object | Реквизиты юридического лица, объект есть всегда |

`legal_entity` содержит `type` (`company`, `individual_entrepreneur` или
`null`), `name`, `inn`, `kpp`, `ogrn`, `ogrnip` (каждое из последних пяти —
`string | null`). Реквизиты необязательны и не проверяются по госреестрам.

Пример архивного филиала:

```json
{
  "id": 7,
  "name": "Центр",
  "address": "ул. Примерная, 1",
  "status": "archived",
  "updated_at": "2026-10-27T10:00:00Z",
  "legal_entity": {
    "type": "company",
    "name": "ООО Пример",
    "inn": "1234567890",
    "kpp": null,
    "ogrn": null,
    "ogrnip": null
  }
}
```

## 4. Снимки и карточки

### `GET /api/v1/external/directory/members`

| Query | Тип и диапазон | По умолчанию | Смысл |
|---|---|---|---|
| `role` | `owner \| manager \| employee` | нет | Отбор по роли |
| `status` | один из статусов участника | нет | Отбор по `Member.status` |
| `location_id` | integer `> 0` | нет | Участники, у которых филиал присутствует в выбранной проекции |
| `include_inactive` | boolean | `false` | Полный режим |
| `limit` | integer `1..500` | `100` | Размер страницы |
| `page_cursor` | opaque string, до 4096 символов | нет | Продолжение ранее созданного снимка |

Пример: `GET /api/v1/external/directory/members?include_inactive=true&limit=100`.
Фильтр `status=terminated` без полного режима даст пустой список.

### `GET /api/v1/external/directory/locations`

| Query | Тип и диапазон | По умолчанию | Смысл |
|---|---|---|---|
| `status` | `active \| inactive \| archived` | нет | Отбор по `Location.status` |
| `location_id` | integer `> 0` | нет | ID самого филиала |
| `include_inactive` | boolean | `false` | Полный режим |
| `limit` | integer `1..500` | `100` | Размер страницы |
| `page_cursor` | opaque string, до 4096 символов | нет | Продолжение снимка |

Пример: `GET /api/v1/external/directory/locations?include_inactive=true`.
`role` для филиалов не принимается.

Оба списка возвращают `200 OK` с одинаковой оболочкой:

```json
{
  "data": [
    {
      "member_uid": "00000000-0000-4000-8000-000000000008",
      "full_name": "Иванов Иван Иванович",
      "role": "employee",
      "status": "terminated",
      "updated_at": "2026-10-27T10:00:00Z",
      "primary_location": null,
      "locations": [],
      "primary_position": null,
      "positions": [],
      "location_scope": "assigned_locations"
    }
  ],
  "page": {"limit": 100, "has_more": true, "next_cursor": "<opaque-page-cursor>"},
  "delta_cursor": "<opaque-delta-cursor>"
}
```

Здесь показан снимок `members` с `include_inactive=true`; у `locations`
оболочка такая же, а элементы `data` имеют формат `Location`.
`data` всегда массив (возможен пустой). Последняя страница содержит
`has_more=false`, `next_cursor=null`; `delta_cursor` доступен даже для пустого
снимка и одинаков на всех его страницах. Порядок: участники по
`member_uid ASC`, филиалы по `id ASC`.

Для следующей страницы вызовите тот же путь с `page_cursor`, полученным в
`page.next_cursor`. Если остальные фильтры, `limit` или `include_inactive`
пропущены, они наследуются из курсора. Явное несовпадение с подпиской даёт
`400 invalid_cursor`. Снимок неизменяем и действует **24 часа с первой
страницы**; последующие страницы не продлевают срок. Новые изменения будут
доступны через `delta_cursor` после завершения снимка. Применяйте все страницы
атомарной заменой локальной копии.

### Детали

- `GET /api/v1/external/directory/members/{member_uid}`: UUID в пути;
  ответ `{"data": <Member>}`.
- `GET /api/v1/external/directory/locations/{location_id}`: положительный
  integer в пути; ответ `{"data": <Location>}`.

Единственный допустимый query у карточек — `include_inactive=true|false`.
Без него неактивная или архивная карточка даёт `404`; с `true` она доступна,
если запись сохранилась в организации интеграции. Чужие, несуществующие и
физически удалённые записи также дают `404` без раскрытия чужого tenant.

## 5. Поток изменений

`GET /api/v1/external/directory/changes?cursor=<delta_cursor>` принимает
обязательный `cursor` (opaque string до 4096 символов) и необязательный
`include_inactive`. Ресурс, организация, фильтры и режим уже закреплены в
курсоре. Явно переданное значение режима должно с ним совпадать. Для
участников и филиалов нужны **два независимых** снимка и два delta cursor.

Ответ `200 OK`:

```json
{
  "data": [
    {
      "sequence": 123,
      "entity_type": "member",
      "entity_uid": "00000000-0000-4000-8000-000000000008",
      "operation": "upsert",
      "occurred_at": "2026-10-27T10:00:00Z",
      "reason": "terminated",
      "data": {
        "member_uid": "00000000-0000-4000-8000-000000000008",
        "full_name": "Иванов Иван Иванович",
        "role": "employee",
        "status": "terminated",
        "updated_at": "2026-10-27T10:00:00Z",
        "primary_location": null,
        "locations": [],
        "primary_position": null,
        "positions": [],
        "location_scope": "assigned_locations"
      }
    }
  ],
  "next_cursor": "<opaque-delta-cursor>",
  "has_more": false
}
```

Это пример **полного** режима: `reason=terminated` при `operation=upsert`.
Ориентируйтесь на `operation`, а не на название причины. Для филиала
`entity_type=location`, `entity_uid` — строковое представление его числового
`id`, а `data` — полный `Location`. `upsert` содержит полный DTO; `remove`
содержит `data=null`. Удаление при выходе из фильтра имеет
`reason=no_longer_matches_filter`. В обычном режиме выбытие участника или
филиала из действующего состава даёт `remove`. В полном режиме сохранённые
изменения статуса дают `upsert`; физическое удаление даёт `remove`.

На один запрос просматривается не более **1000 исходных событий**. После
применения фильтра `data` может быть пустым даже при `has_more=true`.
Сохраняйте `next_cursor` вместе с применёнными событиями в одной локальной
транзакции и продолжайте, пока `has_more` не станет `false`. Повторное
применение событий должно быть идемпотентным. Последовательность `sequence`
общая для организации, поэтому пропуски номеров внутри одного ресурса
нормальны.

Delta cursor действует **90 дней**; журнал также хранится 90 дней. При
истечении срока, разрыве журнала или встрече старого события без полной
проекции в полном режиме API возвращает `410 delta_cursor_expired`. Загрузите
новый полный снимок соответствующего ресурса. Старые курсоры v1 продолжают
только обычный режим; новые v2 связаны с `include_inactive`. При смене
фильтров или режима нужен новый снимок. Курсоры непрозрачны: не разбирайте
и не изменяйте их на стороне потребителя.

## 6. Ошибки и действия клиента

Формат ошибки:

```json
{
  "error": {
    "code": "invalid_cursor",
    "message": "Cursor does not match this request.",
    "details": {}
  }
}
```

| HTTP / `code` | Когда | Действие |
|---|---|---|
| `400 https_required` | Token exchange выполнен без HTTPS | Использовать проверенный HTTPS endpoint |
| `400 invalid_request` | Query на token exchange | Удалить query; credentials передавать в JSON body |
| `401 integration_credentials_invalid` | Не принят `client_id`/секрет | Проверить выданную владельцем версию credentials |
| `401 auth_required` | Нет корректного bearer token на каталоге | Получить новый токен и повторить один раз |
| `403 integration_scope_required` | Неподходящий actor/scope | Использовать integration token с `directory:read` |
| `403 integration_disabled` | Отключён client или организация | Остановить синхронизацию, обратиться к владельцу |
| `400 invalid_cursor` | Не совпали подпись, tenant, ресурс, фильтры или режим | Проверить сохранённый курсор; при смене подписки начать снимок |
| `404 directory_entity_not_found` | Карточка отсутствует в выбранном режиме/организации | Сверить ID и режим; не считать ответ подтверждением существования в другом tenant |
| `410 snapshot_cursor_expired` | Истёк снимок | Начать снимок ресурса заново |
| `410 delta_cursor_expired` | Истёк/разорван поток или full delta встретил старое событие | Начать полный снимок ресурса заново |
| `413 invalid_request` | Тело token exchange больше 4096 байт | Исправить тело |
| `415 unsupported_media_type` | Token exchange без JSON Content-Type | Отправить `application/json` |
| `422 invalid_request` | Неверное тело, параметр, enum, путь или повторный/лишний query | Исправить запрос |
| `429 rate_limited` | Превышен лимит обмена | Выдержать `Retry-After` |
| `503 integration_auth_unavailable` | Авторизация интеграции временно недоступна | Повторить позже с backoff |

Не отправляйте бесконечные повторы при `401`, `403` или неизменном `422`.
При `5xx` оставляйте старый checkpoint и используйте ограниченные повторы.

## 7. Минимальный алгоритм потребителя

1. Получить у владельца `client_id`/`client_secret` по защищённому каналу и
   обменять их на access token.
2. Выбрать режим. Для всех статусов запросить `members` и `locations` с
   `include_inactive=true`, пройти все страницы каждого снимка.
3. Атомарно заменить локальные копии и сохранить отдельные `delta_cursor`
   участников и филиалов.
4. Периодически читать `/changes` для каждого курсора; `upsert` заменяет
   полную запись, `remove` удаляет её из локальной выборки. События и
   `next_cursor` фиксировать вместе.
5. При `410` или смене фильтра/режима снова выполнить снимок нужного ресурса.

Интерактивный вход сотрудника во внешний модуль и SSO этим API не
предоставляются. `role` и сохранённые назначения — справочные данные; для
авторизации действий пользователя во внешнем модуле нужен отдельный контракт.
