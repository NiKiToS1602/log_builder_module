# Спецификация интеграции внешних веб-сервисов с ClearBarn Sign In

## 1. Участники и границы

ClearBarn Staff выступает провайдером OpenID Connect. Он показывает форму входа, проверяет учётную запись и определяет, допущены ли организация и роль пользователя к конкретному сервису. Бэкенд внешнего сервиса обменивает код, создаёт собственную серверную сессию и применяет правила доступа к своим данным и операциям.

Протокол использует Authorization Code Flow, scope `openid`, PKCE `S256` и `client_secret_basic`. В браузере внешнего сервиса хранится идентификатор его сессии. Секрет клиента и токены хранятся на бэкенде. Для фонового чтения каталога применяется [отдельный контракт машинного доступа](API_SPEC_parent_service.md).

## 2. Подключение сервиса

Передайте оператору ClearBarn название сервиса, окружение, точный HTTPS callback, идентификаторы организаций и необходимые роли. Оператор регистрирует отдельного клиента для каждой пары «сервис и окружение», задаёт допуск по `(client_id, organization_id)` и передаёт секрет через согласованное хранилище. При отсутствии допуска вход закрыт. Команды оператора описаны в разделе ClearBarn Sign In файла `backend/README.md` в репозитории ClearBarn Staff.

| Параметр бэкенда | Значение |
|---|---|
| `CLEARBARN_OIDC_ISSUER` | Точный HTTPS origin провайдера без завершающего `/` |
| `CLEARBARN_OIDC_CLIENT_ID` | UUID клиента из реестра этого issuer |
| `CLEARBARN_OIDC_CLIENT_SECRET` | Секрет из хранилища бэкенда |
| `CLEARBARN_OIDC_REDIRECT_URI` | Точный зарегистрированный HTTPS URL обработчика, например `https://service.example/auth/clearbarn/callback` |

ClearBarn сравнивает callback посимвольно, включая порт, путь, query и кодирование. Параметры `code`, `state`, `error`, `error_description` и `error_uri` зарезервированы для ответа и недопустимы в зарегистрированном URL. Для возврата на нужную страницу храните локальный путь в серверной транзакции входа. Проверьте, что путь ведёт внутрь сервиса, прежде чем выполнять редирект.

## 3. Интерфейс провайдера

Получите метаданные по `GET <issuer>/.well-known/openid-configuration`. Сравните возвращённый `issuer` с конфигурацией и используйте опубликованные адреса для входа, токенов, JWKS и интроспекции.

| Метод и путь | Назначение |
|---|---|
| `GET /.well-known/openid-configuration` | Метаданные провайдера |
| `GET /oidc/authorize` | Переход браузера к форме входа или повторное использование действующей сессии ClearBarn |
| `POST /oidc/token` | Одноразовый обмен кода на ID Token и access token |
| `GET /oidc/jwks` | Публичные ключи проверки ID Token по `kid` |
| `POST /oidc/introspect` | Проверка access token и получение текущего контекста доступа |
| `GET /oidc/logout` | Страница подтверждения выхода из текущей сессии ClearBarn |
| `POST /oidc/logout` | Действие формы ClearBarn с CSRF-защитой |

## 4. Вход пользователя

1. На бэкенде сервиса создайте транзакцию входа. Сгенерируйте случайные `state`, `nonce` и `code_verifier` средствами OIDC-библиотеки. Сохраните их на сервере на срок до пяти минут, привязав к браузеру. Для параллельных вкладок храните отдельную запись для каждого `state`.
2. Перенаправьте браузер на `authorization_endpoint` с параметрами `response_type=code`, `scope=openid`, `client_id`, `redirect_uri`, `state`, `nonce`, `code_challenge` и `code_challenge_method=S256`. Библиотека получает `code_challenge` из `code_verifier`.
3. Если ClearBarn показывает форму входа, пользователь вводит ID организации, логин и пароль на стороне ClearBarn. ID организации обязателен в этой форме для различения одинаковых логинов в разных организациях. Внешний сервис начинает вход без `organization_id` в запросе к провайдеру и получает подтверждённое значение при интроспекции. При действующей сессии провайдера форма может быть пропущена. Для повторного выбора учётной записи передайте `prompt=login`.
4. В обработчике callback проверьте, что `state` соответствует незавершённой транзакции этого браузера, и атомарно погасите её. Выполните проверку и для callback с `error=access_denied`. При ошибке покажите отказ или предложите начать вход заново. При успехе передайте `code` на `token_endpoint` с бэкенда.

Используйте OIDC-библиотеку для формирования заголовка HTTP Basic и кодирования полей формы.

```http
POST /oidc/token HTTP/1.1
Host: auth.clearbarn.example
Authorization: Basic <client_secret_basic>
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=<code>&redirect_uri=<encoded_callback>&code_verifier=<verifier>
```

Ответ содержит `id_token`, `access_token`, `token_type: "Bearer"`, `expires_in` в секундах и `scope: "openid"`. Access token непрозрачный. Проверяйте ID Token библиотекой по JWKS с алгоритмом `RS256`, точным `iss`, ожидаемым `aud`, сроком `exp` и совпадающим `nonce`. Идентификатор `sub` содержит UUID `member_uid`. Используйте `(iss, sub)` как уникальный ключ локальной привязки пользователя.

Перед созданием сессии вызовите introspection. Проверьте активность токена, срок, `client_id`, `scope` и соответствие `sub` проверенному ID Token. Храните серверную сессию с `iss`, `sub`, подтверждённым `organization_id`, access token и его сроком. Смените идентификатор сессии после входа и установите cookie с `Secure`, `HttpOnly` и `SameSite=Lax`. Ограничьте срок сессии сроком access token. При истечении запустите новый браузерный вход.

| Срок по умолчанию | Значение |
|---|---|
| Транзакция входа провайдера | 5 минут |
| Код авторизации | До 60 секунд |
| ID Token | 5 минут |
| Access token | До 60 минут в пределах оставшегося срока сессии провайдера |
| Сессия провайдера | 8 часов |

При незарегистрированном callback или неизвестном клиенте ClearBarn показывает локальную ошибку. `400 invalid_grant` при обмене означает, что код погашен, просрочен или не прошёл проверку привязок. `401 invalid_client` означает ошибку клиентской аутентификации или отключённого клиента. При ошибке обмена предложите начать вход заново. При ошибке конфигурации сообщите оператору.

## 5. Проверка доступа на каждом защищённом запросе

Бэкенд сервиса извлекает access token из своей серверной сессии и вызывает `introspection_endpoint` по HTTPS. Кеширование прав между защищёнными запросами нарушит требование отзыва со следующего запроса.

```http
POST /oidc/introspect HTTP/1.1
Host: auth.clearbarn.example
Authorization: Basic <client_secret_basic>
Content-Type: application/x-www-form-urlencoded

token=<access_token>
```

Активный токен получает HTTP `200` и контекст следующей формы.

```json
{
  "active": true,
  "client_id": "00000000-0000-4000-8000-000000000002",
  "sub": "00000000-0000-4000-8000-000000000008",
  "exp": 1893456000,
  "scope": "openid",
  "organization_id": 42,
  "role": "manager",
  "location_scope": "assigned_locations",
  "allowed_location_ids": [101, 103]
}
```

Проверьте структуру ответа, `active`, Unix timestamp `exp`, ожидаемые `client_id` и `scope`, а также совпадение `sub` и `organization_id` с сохранённой сессией. `role` принимает значения `owner`, `manager`, `employee`.

| Роль | `location_scope` | Значение `allowed_location_ids` |
|---|---|---|
| `owner` | `organization` | Все действующие филиалы организации |
| `manager`, `employee` | `assigned_locations` | Действующие филиалы организации с активным назначением пользователя |

Применяйте локальные правила сервиса к каждой операции. Ограничивайте запросы к данным подтверждённым `organization_id`. Для филиальных операций ограничивайте запросы ещё и `allowed_location_ids` при любой роли, включая владельца. Это относится к спискам, чтению по ID, изменению и удалению. Пустой список закрывает филиальные операции. Значения из URL, формы или тела запроса проверяйте по подтверждённому контексту.

| Результат проверки | Ответ внешнего сервиса |
|---|---|
| Сессия отсутствует, токен истёк или провайдер вернул `200 {"active": false}` | Удалить локальную сессию при её наличии, вернуть `401` из API и предложить новый вход |
| Токен активен, операция запрещена ролью, организацией или филиалом | Вернуть `403`. Для чужого ресурса можно вернуть `404` |
| Таймаут, ошибка TLS, `503` провайдера или некорректный ответ | Вернуть `503` до выполнения операции |
| Провайдер вернул `401 invalid_client` | Вернуть `503` и сообщить оператору о клиентской аутентификации |

ClearBarn пересчитывает контекст при проверке. Изменение назначения учитывается на следующем запросе. Блокировка и отзыв допуска приводят к отказу со следующей проверки. Повторное включение допуска требует нового входа с выдачей нового токена. Уже пройденная проверка относится к тому запросу, для которого она была выполнена.

## 6. Выход и защита данных

- При локальном выходе обработайте защищённый от CSRF `POST`, удалите серверную сессию и сохранённые токены, очистите cookie сервиса.
- Для выхода из ClearBarn после локального выхода переведите браузер на `<issuer>/oidc/logout`. Пользователь подтверждает действие на стороне ClearBarn. Токены этой сессии провайдера теряют силу во всех подключённых сервисах.
- Исключите из журналов и трассировок секрет клиента, коды, токены, PKCE verifier, cookie, заголовки `Authorization` и `Set-Cookie`, query callback и заголовок `Location` с кодом. Используйте проверку сертификата TLS на бэкенде.

## 7. Приёмка

| Сценарий | Ожидаемый результат |
|---|---|
| Первый вход, затем повторный переход с действующей сессией ClearBarn | Callback создаёт локальную сессию. Повторный переход проходит без пароля |
| Подменённый callback, чужой `state`, неверный PKCE, повторный код, неверные `nonce` или `aud` | Сессия сервиса отсутствует |
| Вход пользователя с ролью или организацией без допуска | ClearBarn возвращает `access_denied`. Сессия сервиса отсутствует |
| Одинаковый логин в двух организациях | Две привязки `(iss, sub)`. Запросы к данным используют организацию из introspection |
| Чужой филиал и пустой список филиалов | Филиальная операция запрещена, в том числе по прямому ID |
| Удаление назначения | Филиал исключается из следующей проверки доступа |
| Блокировка, отзыв допуска или выход из ClearBarn | Следующая проверка отклоняет старый токен. После восстановления допуска он остаётся недействительным |
| Недоступность introspection | `503`, операция записи или чтения защищённых данных не выполняется |

Для ручной проверки в локальном контуре используйте [ClearBarn Staff](https://127.0.0.1:18447/) и [тестовый внешний сервис](https://localhost:18448/). Тестовый сервис показывает «ура вошли» после успешного входа. Эти loopback-адреса доступны на машине запуска. Для своего сервиса запросите отдельную регистрацию с его HTTPS callback.

В репозитории ClearBarn Staff пошаговый пример приведён в `docs/36_CLEARBARN_SIGN_IN_INTEGRATION_GUIDE.md`, а параметры подключения и сценарии для журналов контроля — в `docs/38_CLEARBARN_SIGN_IN_CONTROL_LOG_HANDOFF.md`.
